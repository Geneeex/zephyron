# Verification scope and test execution

Run `python scripts/verify_repository.py`. Optional figure regeneration is enabled by `--figures` after installing `requirements.txt`. Both commands resolve the repository from the script location, independent of the working directory. The verifier exits 0 only when its requested checks pass; otherwise it exits 1 and records the failed checks in `build/reports/verification_report.json`.

## What the checks establish

| Group | Count | Checks |
|---|---:|---|
| Engineering constraints | 6 | Stationary infeasibility, six-hour duty results, reserve breaches despite later recharge, capacity saturation/curtailment, unserved energy, overloaded camera traffic |
| Engineering reproduction | 6 | Deterministic clean generation; propagation of battery, auxiliary, PV, mass, diameter, motor and arm changes; inconsistent geometry rejection; published scenario values |
| ML mathematical and data-handling fixtures | 33 | IoU cases and invalid boxes; one-to-one class-aware matching and threshold/tie behavior; undefined rates; bounded frame-age admission; group hashing; duplicate rejection; manuscript listing parity and execution |
| Committed data regression | 16 files | Exact bytes and SHA-256 match after temporary regeneration; inventory must match all expected filenames |
| Scenario summary/provenance | 2 comparisons | Identical summary bytes and equal input snapshots/derived parameters/hash records |
| Optional plots | 9 pairs | Successful generation of every expected PNG and SVG from reproduced analytical data |

The 45 counted tests are software unit/regression fixtures. CSV comparisons and plot generation are reported separately, not added to inflate that count. Individual test names and outcomes, source hashes, CSV row/column counts and file hashes appear in the JSON report. Public reports contain repository-relative paths. The report records the Python version and operating system without usernames or local filesystem roots.

## What the checks do not establish

The fixtures do not validate hardware integration, actual motor torque or battery capacity, terrain traversability, sensor calibration, RF coverage, camera latency, detector training quality, object detection accuracy, or safe autonomous motion. Inputs are declared design assumptions and component specifications. The expected values are analytical calculations. Passing the tests demonstrates internal computational consistency for those inputs.

There is no real-world training/test dataset or model benchmark in this repository. Box records and timestamps used by the unit tests are mathematical fixtures. The matcher handles ordinary single-image boxes and is not the official COCO AP evaluator. A future experiment must acquire independent labelled encounters, calibration samples and hardware logs before making performance claims.

## Reproducing individual suites

```sh
python research/test_engineering_reproduction.py
python research/ml/test_validation_primitives.py
python research/ml/listing1_freshness.py
python research/ml/listing2_matching.py
```

The ML suite additionally writes `build/reports/ml_code_checks.json`. The combined verifier loads the same test cases and produces a single report. Committed evidence snapshots are in `research/reports/`; they are generated by actual runs, not manually assigned PASS labels. A new run writes to `build/` so the archived snapshot remains unchanged.

The exact CSV baseline was verified with CPython 3.12.14 on Windows AMD64. The code was executed both from the repository root and from a different working directory. Exact equality across other OS math-library implementations has not been asserted. Plot bytes are not compared because rendering metadata and environment can change without altering numerical values.
